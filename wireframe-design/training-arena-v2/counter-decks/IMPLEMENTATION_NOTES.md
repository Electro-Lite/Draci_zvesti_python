## Layout and interaction

- Wide view: left **user-selected subject deck** with every card name and copy count; center selected candidate's result plus run depth and final-generation candidate list; right **selected counter deck** with every card name and copy count. Deck identities, card colors and copy counts must stay readable without any deck-inspector action. Current database artwork is optional, never a substitute for text/counts.
- Default selection is the actual `top_counter` from the run summary. A mouse/keyboard-accessible list exposes **all legal final-generation candidates**, not only the five visible example rows. Selecting one updates the center W/D/L, sample, rate, right composition and any composition-difference callout together. Preserve list selection and scroll position while details refresh.
- Head-to-head result is **selected counter versus the user's selected deck**. Label `counter win rate = counter_wins / games`; draws and subject wins use the same all-games denominator. The 100%-stacked result bar is **green = selected counter wins**, **gray = draws**, **red = selected deck wins**; all three segments must match displayed W/D/L counts and rates. **Render each segment's own percentage inside that colored portion** when it fits (example: 80% / 10% / 10%), with legible contrast. For a zero or too-narrow segment, show its percentage immediately adjacent to the bar, keyed to that color, so no category silently disappears and labels never overlap. The counts remain above the bar. Use underlying counts for geometry and percentages; handle rounding so the displayed shares are understandable and the bar fills exactly 100%. Blue remains a deck-identity accent for the subject, not the result bar's win color. Never render a single green fill that hides the draw/loss composition.
- Clearly separate the selected candidate's sample from pooled results across the counter population and from controller-learning games. Show per-candidate games, final candidate count, counter/controller generations, configured two controller populations (15 genomes each currently), estimated learning work, observed validation work and estimated total separately. If a result sample is below 1,000, show a visible **“Exploratory sample · below 1,000-game comparison target”** warning near the rate. Do not describe the top-ranked counter as universally superior: ranking 20 candidates on noisy tests has selection bias even at 1,000 games.
- At 1280×720, retain readable type with panel or list scrolling. At 640×480, stack subject deck → selected result/run depth → candidate list → selected counter deck; all content and controls remain keyboard reachable. Never silently truncate either 10–12-card composition or the candidate list. Keep run identity/status, Back to runs and existing safe Stop training affordances.

## Data model, provenance and arithmetic

`TrainingJob.request` supplies `kind`, subject `deck_id`, `outer_generations` (counter generations), `evaluator_generations` (persistent controller generations), and `evaluation_games` (validation games **per candidate**). `neat_ai/counter_deck_trainer.py::build_summary()` writes the subject deck ID/name and **subject card IDs snapshot**, final `counter_matchups`, `top_counter`, `settings`, pooled `evaluation` and per-outer-generation pooled `skill_evaluations`. Each final candidate row contains `builder_id`, `deck_id`, `deck_name`, `generation`, `cards` (card IDs snapshot), `card_names`, `games`, `counter_wins`, `draws`, `subject_wins`, `counter_win_rate`, `counter_fitness`, and `shared_cards`. Prefer these explicit fields; check that W+D+L=`games` and rederive rate from counts. Candidate rows, not pooled `evaluation`, drive the selected-candidate center result.

The existing `TrainingInsights` exposes only top-counter name/rate and a population count, so add a small read-only mission-specific presentation adapter rather than reading/parsing raw JSON during every Pygame draw. `counter_matchups` is the **final completed outer generation's candidates**, not a history of every candidate in every generation. A running job's summary is written only after an outer generation completes. During its first in-progress generation, show phase/progress and “No counter decks evaluated yet”; do not fabricate partial candidate scores from progress telemetry. After a completed generation, show its genuine candidates and clearly mark run status/partiality until the whole run finishes.

Prefer saved `subject_cards` and candidate `cards` as composition identities; the candidate also saves `card_names`. Resolve live card metadata (names/colors) by ID only as enrichment. Unlike duel summaries, the counter summary **does** snapshot card IDs. If the subject deck is missing/changed later, do not replace its historical card IDs with the current database composition without a clear label. If metadata is missing, show saved name or ID and quantity rather than dropping the row. Group duplicate IDs into counts; show total and distinct card counts derived from the selected snapshot. `shared_cards` means shared **copies**, not just shared names; when displaying a comparison sentence, compute/verify from both ID multisets.

The trainer's builder population is configured for **up to 20** genomes, but some generated decks may be illegal. Therefore planned candidate count can differ from actual `counter_matchups` length. Each legal candidate gets `evaluation_games` seat-balanced tests (the even game index alternates seating). The design's illustrative one-counter-generation, ten-controller-generation example assumes **20 legal candidates × 1,000 tests = 20,000 validation games**. Two persistent controller populations with configured size 15 make **15×15 = 225 learning games per controller generation**, or about **2,250** at ten generations; planned total is about **22,250 simulations**. Learning counts are configuration-derived estimates unless logged exactly. Do not count the same A-vs-B learning game twice because it gives both genomes a fitness contribution. `matches_per_genome` is a *deck-evolution* setting and does not describe counter candidates. Do not present 22,250 as measured/completed if some candidate decks were invalid or the run is partial.

The wireframe uses real saved deck/card compositions but **invented 1,000-game outcomes**: selected Counter G1 #8 wins 800, draws 100 and loses 100. A historical local run for that composition only played 20 validation games (16/2/2), so runtime UI must use the actual selected run and flag it as exploratory. Do not import example card names or sample scores as fallback data.

## Comparison-size product rule

Treat **1,000 validation games per candidate** as the user-requested minimum target for a stable comparison. Recommend/default new counter-evaluation runs to at least 1,000, keep the even/seat-balanced rule, and update any affected setup preset descriptions and workload estimates. A smaller quick diagnostic may remain possible, but it is explicitly **exploratory**, and no “reliable”, “consistent” or definitive counter claim is shown. Historical sub-1,000 runs remain readable, unchanged, and flagged—never rejected, rewritten, or inflated. The threshold is a product convention, not a statistical proof; an optional interval/methodology view must still explain sampling variation and top-of-20 selection effects. A counter found against one selected deck/controller pairing is not a universal counter.

This same convention applies to Duel 2's evaluation **per checkpoint**, whose updated artboard uses 1,000 games/checkpoint. Preserve Duel 2's actual historical samples and warning behavior rather than silently imposing example values. Deck evolution has different experiment structure and is **not** assigned a 1,000-games-per-candidate rule by this handoff.

## States and acceptance

- No candidate summary yet: status/progress and honest empty state; no 0% result, invented top counter or placeholder deck list masquerading as data.
- Completed outer generation while run continues: show real candidates with “run still evolving” or equivalent; selecting a candidate is stable and updates the result/composition together.
- Completed job: all final legal candidates browseable, default top candidate consistent with trainer's rate-then-fitness tie-break; no stale selection from a previous run.
- Failed/cancelled/interrupted: preserve real partial result if available and clearly label it partial. Zero-game/malformed candidate rows show unavailable rate rather than division by zero.
- A 20-game historical result renders as 20 games with exploratory warning; a 1,000-game result renders without the below-target warning, but without certainty claims.
- Subject and counter card lists show all copies, or explicit metadata-unavailable rows with IDs. Same card appears in both lists with correct copy counts.
- Automated tests cover candidate selection, rate/denominator and green-gray-red segment totals/labels (including zero and narrow segments), pooled-vs-candidate separation, tie-break/default, missing/invalid data, card grouping and shared-copy counts, planned-vs-actual workload, low-sample warning, and mission routing. Visual smoke checks at 1600×900, 1280×720 and 640×480 verify scrolling/focus and no clipped content.
