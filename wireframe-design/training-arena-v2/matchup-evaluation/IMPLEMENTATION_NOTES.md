## Data and exact meanings

Runtime values come from the selected run, **never** from example artboard values. `TrainingJob.request` carries `kind`, `deck_id`, `opponent_deck_id`, `evaluator_generations`, and `evaluation_games`; a job's `summary.json` is written after each completed checkpoint, so partial runs can have valid data. `neat_ai/matchup_trainer.py` writes `deck_id`, `deck_name`, `opponent_deck_id`, `opponent_deck_name`, `settings`, `evaluation`, and `skill_evaluations`. Each checkpoint has `generation`, `games`, `deck_1_wins`, `draws`, and `deck_2_wins`; compatibility aliases `ai_wins` and `random_wins` also exist. Prefer the explicit deck fields and validate W+D+L against `games`. The `evaluation` object describes the last completed checkpoint; do not assume it is final until its generation reaches the requested final generation.

Card compositions are **not** snapshotted in matchup summaries. Resolve both deck IDs against current `utils/decks.db` through an existing deck-loading path such as `DBUtil.load_deck()`. Group actual card copies by stable card ID/name and display counts and color. Treat the lookup as a **current database composition**, not proof of the deck's historical training-time composition; label this in the UI or methodology. If a deck or card metadata is unavailable, retain the deck ID/name and show a clear “Composition unavailable” state, never a made-up or stale list. Same-deck-versus-same-deck runs still need separate Deck A and Deck B perspectives.

For each checkpoint, calculate `A% = deck_1_wins / games`, `draw% = draws / games`, and `B% = deck_2_wins / games`; all three shares use **all games** as denominator and sum to 100% before rounding. Do not calculate a conditional non-draw win rate under the same label. Seat-balanced evaluation uses `evaluation_games / 2` seed pairs, each played in both seating orders. Generation labels should come from recorded rows, not hard-coded 1/10/25/40.

`neat_ai/configs/neat_config_evaluator.txt` currently sets `pop_size = 15` for each of two coevolving controller populations. `neat_ai/deck_evaluator.py` pairs every Deck A genome with every Deck B genome once each learning generation. With configured populations of 15+15, a genome enters **15 learning games per generation**, and the generation schedules **15×15 = 225 distinct games**, not 450. At 40 generations, that is about 9,000 learning games. This is a **configuration-derived workload estimate** unless actual game counts are available. It is not `TrainingRequest.matches_per_genome` (that field belongs to deck evolution), and 15 is not the number of fixed controllers throughout the run.

`neat_ai/training_plan.py::matchup_checkpoints(generations)` selects a generation-1 baseline, reached standard checkpoints, and the final generation. At 40 generations it returns (1, 10, 25, 40). `neat_ai/deck_evaluator.py::holdout_checkpoint_generations()` excludes the final generation from its intermediate pass; the final holdout runs **once**, not twice. Each updated example checkpoint has **1,000** new seat-balanced evaluation games, so **4 × 1,000 = 4,000 separate evaluation games**. Total example workload is **about 13,000 simulated games**: 9,000 learning + 4,000 evaluation. The final 53% Deck A rate in the wireframe comes from **530 of the final checkpoint's 1,000 games**, not 53% of 4,000 or 13,000. Actual settings and completed checkpoint counts may differ. Show “planned” versus “completed/recorded” explicitly, especially for running or interrupted jobs.

The design now treats **1,000 evaluation games per checkpoint as the minimum target for a stable comparison**. Recommend/default to at least 1,000 for new comparison runs; if quick diagnostics or historical jobs use fewer games, still display actual results but mark each affected checkpoint **“exploratory sample · below 1,000-game comparison target”** and avoid conclusive language. The threshold is a user-requested product convention, not a statistical guarantee; do not claim that 1,000 games prove causation or generalize beyond the tested decks/controllers. Keep any setup preset/default change explicit and update workload estimates/tests accordingly; do not retroactively reject or rewrite old summaries.

The current `TrainingInsights` tuple simplifies checkpoint outcomes and omits full per-checkpoint names/settings/composition. Prefer a small, read-only mission-specific presentation adapter over spreading raw JSON parsing through draw code. Keep any file/database loading and aggregation outside the Pygame draw loop. Refresh or invalidate when partial `summary.json` gains a checkpoint, and preserve the existing asynchronous insight-loading pattern if practical. No runtime dependency on the SVG renderer.

## States and acceptance

- No summary yet: deck identities/status can appear, but checkpoint region says evaluation pending; no fabricated 0% win rate.
- Running with partial summary: show only completed checkpoints and mark the next expected one pending; final reading says pending until final exists. Workload is planned/estimated, not an observed result.
- Completed: all recorded checkpoints shown; final reading uses the actual final-generation row. If final row is missing or malformed, show incomplete-data state rather than a false final.
- Failed/cancelled/interrupted: retain genuine partial results with status, and do not imply completion.
- Missing/deleted deck or card metadata: show IDs/names and explicit composition unavailable. Empty 0-game checkpoints do not produce percentages or divide by zero.
- Same deck on both sides: separate A/B labeling survives identical names and compositions.
- An older 100-game checkpoint remains visible as 100 games, flagged exploratory; no substitution of the illustrative 1,000-game example.
- Counter and evolution details: blank, mission-labeled placeholders only. Their training, Runs visibility and safe stop path still work.
- Automated tests cover parsing, W/D/L denominators and perspective, 15×15 counting, checkpoint arithmetic, incomplete/malformed inputs, missing deck lookup, placeholders, and navigation. Visual smoke checks at 1600×900, 1280×720, and 640×480 show no overlap or clipped deck/checkpoint content.
