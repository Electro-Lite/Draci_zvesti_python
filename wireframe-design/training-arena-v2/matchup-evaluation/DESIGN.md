# Fixed-deck matchup evaluation

Question: **How does Deck A fare against Deck B after their controllers learn?** Unlike counter training, both deck identities stay fixed. The user should never have to infer which deck owns a win rate or a fitness value.

Two directions:

1. [Two-sided scoreboard](01-two-sided-scoreboard.png) gives Deck A and Deck B equal visual weight, shows both complete card lists, and writes “Deck A win rate”, “Deck B win rate” and “draw rate” separately. It is fastest to read at the final checkpoint.
2. [Checkpoint study](02-checkpoint-study.png) emphasizes the learning trajectory. Each checkpoint row has an explicit A / draw / B share, not a lone unlabeled line. Both complete deck compositions remain visible in the left panel; there is **no full-deck button or separate inspector action** in this chosen direction. The [full deck inspector](03-deck-inspector.png) remains an unselected study, not part of the implementation target.

Starter Blue and Killer Queen compositions in the examples are the actual saved decks from `utils/decks.db`: Starter Blue has Lucisnik, Paladin, Panos, Pesak and Strazny ×2 each; Killer Queen has Novic ×4, Zabijak ×4 and Asketa ×2. The example **530 Deck A wins, 140 draws and 330 Deck B wins in 1,000 games** is invented for the wireframe. `Deck A win rate = Deck A wins / all games`; Deck B uses the same denominator, and draws are a separate share. A different conditional non-draw rate must have a different label.

The chosen **Checkpoint study** screen now exposes its illustrative run depth beside the trend: **two evolving controller populations of 15 genomes each per generation** and **40 learning generations**. Each Deck A genome plays one learning game against each of the 15 Deck B genomes, and vice versa: **15 learning games per genome per generation**, or **225 distinct learning games per generation** (not 450, because each game counts for both genomes). Across 40 generations that schedules about **9,000 learning games**. The 15 genomes are the configured population size in each generation, not 15 unchanged controllers carried through the whole run.

“Checkpoint games” means **fresh evaluation games using the selected controllers at that stage**, separate from the all-pairs learning games. Four checkpoints (generations 1, 10, 25 and 40) each use **1,000 seat-balanced evaluation games**: **4 × 1,000 = 4,000 checkpoint games**, bringing the illustrative workload to **about 13,000 scheduled simulations** overall. The final Deck A win rate of 53% uses only **530 wins in the final checkpoint's 1,000 games**—not all 4,000 checkpoint games or 13,000 simulations. These are coherent example values, not measurements of the saved Starter Blue / Killer Queen pairing. `matches_per_genome` is not a duel-trainer user setting; “15 games per genome per generation” describes the current all-pairs learning schedule, not a configurable knob or the genome's lifetime total. A checkpoint with fewer than 1,000 evaluation games remains readable, but is marked as exploratory and below the comparison target.

`neat_ai/matchup_trainer.py` writes `deck_id`, `opponent_deck_id`, names, final W/D/L and per-checkpoint W/D/L, including the generation-one baseline. The summary does **not** snapshot compositions; a future UI can look up current saved deck lists by ID, but must label them as current database records and report “composition unavailable” if the deck is missing. Results must never imply that reconstructed cards are an immutable training-time snapshot.

For a running job, show completed checkpoint rows and clearly mark the next one pending. Retain both seating orders' balance context and total game counts. If the user chooses the same deck on both sides, keep the A/B labels even when names are identical. A win rate confidence range can appear in a methods drawer, with its denominator and descriptive nature explained.
